# Phase 1H-A schema reconciliation review

These files are proposals, not active migrations. No database writes or migration commands
were executed. The SQL was generated offline with Prisma migrate diff between schema files,
using an explicitly selected prisma.config.ts. No datasource/shadow database was used.

Their physical names are the same quoted model names. No migration SQL creates them or
BookingType, BookingStatus, BookingModel. Commit 803fcea added the models and changed

and ContactMessage.status default NEW also lack migration SQL.

a migration-derived inventory rather than a freshly authenticated catalog result.

The current tool session has no local password/pgpass credentials. Its read-only psql

## Proposed changes

01-contact-status-enum.review.sql adds NEW to the existing contact enum. Commit this change
before using NEW as a default. 02-booking-contact-schema.review.sql creates three booking
enums/tables, primary keys, the unique reference, seven additional explicit indexes in total
(one unique and six non-unique), and three foreign keys; it also adds nullable serviceType
and changes the contact status default. Existing OPEN/CLOSED labels and existing rows remain.

The SQL has no DROP, DELETE, TRUNCATE, enum replacement or existing-row rewrite. Booking
IDs are generated by Prisma's cuid() behavior, not SQL defaults. The optional Booking.userId
foreign key uses SET NULL; passenger/history foreign keys use CASCADE; updates use CASCADE.
Schema-level default changes apply to future inserts, not existing contact values.

The modeled baseline was derived from the current schema by removing exactly the three
booking models/enums and reverting the unmigrated contact additions. It is consistent with
the migration DDL reviewed, but is not a complete authenticated live-database diff. Existing
objects/types or additional live drift require reconciliation before these drafts are promoted.

## Integration preflight gap

The prepared serial runner checks migration names, outbox timestamp precision, idempotency
uniqueness and an empty queue. It does NOT currently prove Booking tables, child foreign keys,
booking indexes or contact columns/enums exist; it also does not compare migration checksums.
Therefore all five completed migration names can pass preflight despite this schema gap.
Before write tests, extend preflight to check required tables/columns, enum values, foreign
keys and index definitions; do not substitute migration-record count for schema parity.

The six inquiry cases do not directly create bookings. However, the ten-case reliability
suite creates bookings and children, and its cleanup queries Booking even for non-booking
cases. The combined 16-case runner must not execute against the reported missing-table schema.
The six inquiry cases also remain subject to authentication/schema/isolation/cleanup approval.
